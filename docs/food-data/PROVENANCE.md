# 食物营养数据溯源与质量验证

> 这份文档回答一个具体问题：**App 里显示的热量，凭什么说它是对的？**
>
> 结论先说：本工程**没有手工编写任何一条营养数值**。1840 条食物全部来自权威数据库
> 或按可复算的配比推算，每条都带条目号可回溯；数据入库前过 5 道质量闸门，
> 并与第二个独立权威库做了交叉核对。**全部条目都是简体中文名，没有一条英文名。**

---

## 一、数据源

### 1. 主数据源：《中国食物成分表 标准版（第 6 版）》

- 内容范围：「能量和食物一般营养成分」表，即每 100g 可食部的能量、蛋白质、脂肪、碳水化合物。
- 结构化形式来源：开源项目 [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)
  （含原书表格截图与逐条转录的 JSON，本工程使用其 `json_data_v3_20260825_qwen38max_kimi_k3_fixed` 目录，
  该目录是经过一轮校对/修正的版本）。
- 为什么选它：这是国内营养与临床领域通用的食物成分表，也是「中式食物热量」最权威的中文口径。
- 采纳条目：**1656 条**（含 23 条同名条目去重，最终入库 1633 条）。
- **覆盖边界（必须说清楚）**：这份公开数据只有 1677 条，分类全部是**原料级**
  （谷类/薯类/干豆/蔬菜/菌藻/水果/畜肉/禽肉/乳类/蛋类/鱼虾蟹贝/坚果种子/油脂/淀粉）。
  它**没有**小吃、糕点、菜肴、饮料、调味品这几类。

  所以：主食里的米饭/馒头/面条/粥/米粉/粉丝/烙饼/烧饼/油条**是有的**（这些属于谷类制品），
  但「饺子、包子、宫保鸡丁、薯片、可乐」这类**不在**其中 —— 见第二、三节的处理办法。

| 分类 | 条数 | 分类 | 条数 |

| 蔬菜 | 372 | 谷薯 | 152 |
| 肉蛋 | 311 | 豆类 | 82 |

（上表为最终库内分布，含 USDA 与复算菜肴补入的部分。）

### 2. 第二数据源：USDA FoodData Central · SR Legacy（**只取人工审定的子集**）

- 公有领域（public domain），美国农业部官方发布，共 7,793 条食物的每 100g 营养值。
- **它同时承担两个角色**：给成分表没有的食材（芝士、意面、牛油果、燕麦、可乐…）提供数值；
  以及作为独立来源与成分表做交叉核对。

**为什么不整库导入（这是一个被修正过的设计）**：7,793 条里包含 954 条牛肉细分切法、
464 条羊/小牛肉、345 条婴儿食品，以及大量品牌商品（`Candies, ALMOND JOY Candy Bar`）和英文专名。
早期版本曾经全量导入，结果是食物库「一半条目是英文名」——
实测中手动录入页真的出现了 `Cheese, gruyere`、`Oil, beluga, whale (Alaska Native)` 这种条目。
对一个中文 App 来说这既搜不到、也没法看。

现在的做法是**人工审定**（`tools/food_naming.py`）：

- 只保留中国人日常真的会吃到的条目，**命名表 166 条、实际入库 165 条**（其中「柠檬水」因 USDA 只有粉冲/浓缩款、与中文语境不符而**下架**）；
- 每条给出**简体中文名**（`Cheese, cheddar` → 切达奶酪，`Avocados, raw` → 牛油果）；
- 英文原名保留在 `alias` 字段里：**只参与检索，不在界面上显示**（用英文搜也能搜到，但看到的永远是中文名）；
- 命名不了、或只匹配到「低脂/婴儿食品/阿拉斯加原住民」这类变体的，一律不入库；
- 成分表已经覆盖的食物不再从 USDA 重复导入（避免搜出两条「胡萝卜」）；
- 审定表里挑不到条目的项会被脚本报出来（本次 0 条未匹配、0 条重复指向）。

### 3. 复算菜肴：42 道（配比透明，可逐条复算）

见第二节。

> 上表后 10 条（麻辣香锅 / 肉夹馍 / 凉皮 / 麻辣烫 / 烤冷面 / 鸡蛋灌饼 / 酸辣粉 / 葡式蛋挞 / 炸串 / 奶茶）
> 是 2026-10 补的中式街头小吃与饮品——这四类在成分表**公开转录**里没有对应分类，但都能用成分表食材
> 按显式配比复算出来，所以走的是和家常菜完全相同的一套机制（每个食材带条目号，可逐条复算）。
> 几个必须说清楚的口径：**凉皮只计「成品中保留的水」**（洗面/蒸制用水被滤掉，与汤类相反，否则每 100g 值会被
> 稀释掉一大半）；**麻辣烫/酸辣粉的汤按会被喝掉计**；**奶茶不含珍珠**（成分表公开转录里只有生「木薯」，
> 没有木薯淀粉，不拿它当珍珠）；**炸串的吸油量按中位取**（10~35g 油约差 40 kcal/100g）。

计算口径（三条，都在结果页可改份量）：

1. **按投料总重折算**：每个食材按 `每100g值 × 克数 / 100` 累加后，除以成品总重。
2. **主食类要把「吸水」写进配方**：挂面 100g 煮熟约 250g，所以配方里写成
   `面条（生）100g + 水 150g`；粽子的糯米、饺子的和面水同理。
   不这么做的话，一碗面会被算成「干面条的浓缩值」，热量虚高 1.5 倍以上。
3. **汤类必须把水计入成品重量**，否则一碗汤会按浓缩汁算，热量会虚高好几倍。
4. **用油量取家常中位值**，并在每条备注里写明。**用油量是炒菜热量波动的主因**
   （同一道菜 5g~25g 油对应约 80~130 kcal/100g 的差距），正因如此结果页的份量必须可改。

**这部分数据的诚实边界**：食材数值来自权威库，但**配比是家常中位假设**，不是实验室实测的成品值。
一道「红烧肉」按 349 kcal/100g 的软五花算是 332.6 kcal/100g，若用 568 kcal/100g 的肋条肉则接近 500。
界面上这类条目显示为「按中国食物成分表第6版食材值 + 显式配比推算」，
并且**优先让用户改份量**，而不是把假设藏起来。

## 三、五道质量闸门

生成脚本 `tools/build-food-db.py` 对每条数据执行以下检查，**不通过就不入库**：

| 闸门 | 规则 | 本次结果 |
|---|---|---|
| A. 完整性 | 热量必须存在；碳水/蛋白/脂肪缺失时按 0 处理（成分表用「—」表示未检出/微量） | 缺热量者被拒 |
| B. Atwater 自洽 | \|4×碳水 + 4×蛋白 + 9×脂肪 − 自报热量\| 需满足 ≤40% 相对偏差 **或** ≤25 kcal/100g 绝对差 | 18 条不自洽被拒 |
| C. 绝对区间 | 0 < 热量 ≤ 950 kcal/100g（纯油脂约 900） | 无越界 |
| D. 唯一性 | id 不得重复；**中文名也不得重复**（同名条目搜索时无法分辨） | 0 条重 id，23 条同名去重 |
| E. 交叉核对 | 与 USDA 同食材比对热量差异 | 11 项一致（≤25%），1 项标注待人工复核 |

三条需要解释的规则：

1. **闸门 A 的「按 0 处理」不是拍脑袋填 0**。填 0 之后必须过闸门 B ——
   也就是「0」这个假设要被热量数据自己证明。例如花生油 `能量 899 / 碳水 — / 蛋白 Tr / 脂肪 99.9`，
   按 0 处理后 Atwater 反算 9×99.9 = 899.1，与自报 899 差 0.01%，说明这两个 0 是真的。
   反之，一条 `热量 200 / 碳水 —` 的记录会被闸门 B 拦下。本次 26 条走了这个流程。
2. **闸门 B 的绝对差下限（25 kcal/100g）**：热量本身极低时（如蒸馏醋 18 kcal/100g）
   相对偏差会被放大到几百 %，但绝对差不到 1 kcal，这种不算问题。
   没有这条下限，白醋会被误杀，而白醋是「醋溜土豆丝」这类菜的必要食材。
3. **Atwater 闸门有明确豁免，且豁免逐条出现在报告里**：酒类的能量主要来自乙醇（7 kcal/g）、
   醋来自醋酸，都不在 4/4/9 口径内，USDA 的能量值本身包含这部分。
   本次豁免 4 条（啤酒、红葡萄酒、白葡萄酒、清酒），全部列在 `qa_report.json` 的 `atwaterExempt` 字段。
   **豁免范围必须看得见，不能悄悄放宽整个闸门。**

被拒的数据**不会被估算值替代**，直接弃用——宁可库里少一条，也不让用户看到一个假数字。
本次共拒收 21 条，明细见报告。

| 花生油 | Oil, peanut, salad or cooking | +1.7% | 一致 |
| 黄豆［大豆］ | Soybeans, mature seeds, raw | −12.6% | 一致（碳水口径差异，见下） |
| 白萝卜（鲜）［莱菔］ | Radishes, raw | 0.0% | 一致 |
| 番茄［西红柿］ | Tomatoes, red, ripe, raw | −16.7% | 一致（均在 25% 内） |
| 小麦粉（代表值） | Wheat flour, white, all-purpose | −1.4% | 一致 |
| 猪肉（代表值，fat30g） | Pork, fresh, composite of trimmed retail cuts, raw | +53.2% | **待人工复核** |

两点必须说清楚：

1. **中美的碳水口径不同**：成分表的碳水化合物为「可利用碳水」，
   USDA 为「差减法碳水（含膳食纤维）」。豆类、蔬菜这类高纤维食物因此天然存在 10%~20% 差异，
   所以阈值定在 25% 而不是 5%。这是口径差异，不是错误。
2. **猪肉那一项被标为待复核**：「猪肉（代表值，fat30g）」是按脂肪含量聚合的代表值，
   与 USDA 的某个美国部位复合值本来就不是同一对象，热量差 53% 属于**比对口径不成立**，
   而不是数据错。工程上不把它当成错误数据自动采信，保留在报告里由人判断。

## 五、界面上不会出现英文名的三层保证

1. **数据层**：入库的每一条都有简体中文名（本次构建校验：**1840 条中 0 条不含汉字**）；
   命名不了的英文条目根本不进库。
2. **检索层**：USDA 英文原名只放在 `alias` 字段参与 SQL 匹配，UI 从不渲染该字段。
3. **升级层**：食物库不只是「加条目」也会「删条目」（例如剔除那批英文条目）。
   所以种子升级是**整表重灌**而不是增量 upsert，并且会校验条目数
   （`food_items` 中种子条目数 == 种子版本号里的条目数），
   自愈「装过中间版本、升级被中断」这类残留状态。
   删除范围严格限定 `ai_estimated = 0`：用户自己存的「我的食物」不受影响；
   历史记录在 `entry_items` 里存的是快照（名称 + 数值），同样不受影响。

## 六、复现方式

```powershell
# 1) 拉取权威数据源（成分表 + USDA，约 40 MB）
powershell -File tools\fetch-sources.ps1
# 2) 生成种子库 + 质量报告
python tools\build-food-db.py
# 3) 单独核对某一批数值（抽查用）
python tools\probe-values.py "猪肉（前臀尖"
python tools\probe-values.py --dishes
```

产物：

- `app/src/main/assets/foods_seed.json` —— App 随包食物库（1840 条，全中文名）
- `app/src/main/assets/foods_seed.version` —— 种子版本号（`条目数-内容哈希`）
- `tools/data/reports/qa_report.json` —— 拒收清单、USDA 交叉核对、命名未匹配/重复、Atwater 豁免明细

要新增一条数据，**只能**改数据源、`USDA_PICKS`（中文命名表）或 `RECIPES` 里的配比，
不能直接往 JSON 里写数值 —— 否则下一次跑脚本就被覆盖，这也是一种保护。

## 七、数据修订流程

1. 发现某条数值可疑 → 先在 `tools/data/reports/qa_report.json` 与成分表原书截图
   （数据源仓库内的截图目录）中核对条目号；
2. 若确为转录错误 → 在 `RECIPES`/命名表/映射表层面处理，或升级数据源版本；
3. 重新跑 `build-food-db.py`，并核对 `counts` 与拒收清单；
4. 装到设备上确认库已更新（`python tools\check-db-count.py`）；
5. 已记录的历史餐次**不会**被改写：`entry_items` 里存的是当时的快照（克数 + 各项数值），
   库值变化只影响之后的新记录。这是「历史数据可信」这条底线。
