# 热量记录 App（CalorieTracker）

拍一张饭菜照片，自动识别出菜品和热量，一键记入当天。
面向中文市场的泛减脂人群，核心是三件事：**越快越好、越少填越好、视觉上不制造焦虑**。

> 一句话原则：**识别服务只负责猜「是什么、多重」，热量永远由本地权威食物库换算。**
> 任何一处热量数字都能按条目号回溯到《中国食物成分表》或 USDA。

## 二、跑起来

### 1. 需要的环境

- JDK 17（AGP 8.7 要求；系统默认 `java` 若是 1.8 会直接构建失败）
- Android SDK：`platforms;android-36` + `build-tools;36.0.0` + `platform-tools`

### 2. 编译

```powershell
# 直接用本机 Gradle（需要先设 JAVA_HOME / ANDROID_HOME）
powershell -File tools\build.ps1
```

或手动：

```powershell
$env:JAVA_HOME = "<path-to-jdk17>"
.\gradlew.bat :app:assembleDebug
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

### 3. 装机

```powershell
# 真机（USB 调试）
adb install -r dist\CalorieTracker-1.0.0-debug.apk

# MuMu / 雷电等模拟器：先连 adb，再装
adb connect 127.0.0.1:16384
adb install -r dist\CalorieTracker-1.0.0-debug.apk
```

一键编译装机：`powershell -File tools\build.ps1 -Install`

首次运行需要授予**相机权限**（没有也能用：会走到手动录入）。

### 4. 三个环境坑（都已在仓库里处理好）

1. **工程路径含中文**（`E:\AI开发`）会让 AGP 直接拒绝构建 →
   `gradle.properties` 里已加 `android.overridePathCheck=true`（AGP 官方开关）。
2. **中文路径还会让 Gradle 的测试 JVM 找不到测试类**（`ClassNotFoundException`）。
   这是 Windows 下 Gradle test worker 的 classpath 编码问题，改 `jvmargs` 无效；
   唯一稳妥的办法是给工程映射一个 ASCII 盘符再跑：
   ```powershell
   subst X: "E:\AI开发"
   ```
   `tools\build.ps1` 与 `tools\test.ps1` 已经**自动**做这件事：
   检测到非 ASCII 路径就自动 `subst` 到 X:/Y:/Z: 再调用 Gradle，产物仍落在原目录。
   不想用这套变通的话，把工程整个挪到纯 ASCII 路径（如 `D:\projects\calorie-tracker`）即可。
3. `local.properties` 里的 `sdk.dir` 指向本机 SDK，**不要提交**。

## 四、热量为什么是准的

完整论证与核对明细见 **[docs/food-data/PROVENANCE.md](docs/food-data/PROVENANCE.md)**，这里给结论：

1. **食物库 1840 条，零手工编写，且全部是简体中文名**，分三层：
   - **主源 1633 条**：《中国食物成分表 标准版（第 6 版）》，主食/蔬菜/肉蛋/水产/乳/水果/豆/坚果/油脂，
     每条带 `sourceRef` 条目号；
   - **复算菜肴 42 道**：番茄炒蛋、宫保鸡丁、红烧肉、饺子、包子、汤圆、粽子…
     按显式配比推算，配比与算式写死在 `tools/build-food-db.py` 的 `RECIPES` 里，逐条可复算；
   - **第二源 165 条**：USDA FoodData Central（SR Legacy，公有领域）**人工审定的子集**，
     覆盖意面/芝士/希腊酸奶/牛油果/三文鱼/可乐/薯片/披萨这类成分表没有的食材，
     每条都由人写了简体中文名（英文原名只参与检索、不显示）。
2. **不导入英文条目**：USDA 那 7793 条里绝大多数是牛肉细分切法、婴儿食品、品牌商品和英文专名。
   全量导入的结果是手动录入页出现 `Cheese, gruyere`、`Oil, beluga, whale`——一个中文 App 不该是这样。
   现在**命名不了的一律不入库**，构建时校验「0 条不含汉字」。
3. **五道质量闸门**：完整性 / Atwater 自洽 / 绝对区间 / id 唯一 / USDA 交叉核对。
   不通过的数据直接弃用，**不用估算值顶替**；酒类等「能量来自乙醇/有机酸」的豁免逐条写进报告。
4. **用 USDA 做独立交叉核对**，12 项基础食材中 11 项一致
   （热量偏差 ≤ 25%，差异主要来自中美碳水口径不同），1 项标注待人工复核。
5. **换算只有一个入口**：`NutritionMath.scalePer100g(每100g值, 克数)`。
   热量直接取数据库自报值线性缩放，绝不用 Atwater 反算去覆盖权威值。
6. **历史记录不可篡改**：`entry_items` 存的是「克数 + 当时的各项快照」，
   日后库值更新不会改写用户的历史记录。
7. **升库会重灌而不是只加不减**：食物库也会「删条目」，所以种子升级按内容哈希整表重灌，
   并校验条目数是否等于种子版本号里的数目，能自愈「装过中间版本/升级被中断」的残留状态。

**覆盖边界（不粉饰）**：那份公开的成分表数据只有 1677 条，且全是原料级分类，
**没有**小吃、糕点、菜肴、饮料、调味品。所以主食里的米饭/馒头/面条/粥/油条是有的，
饺子包子这类点心、宫保鸡丁这类菜、可乐薯片这类零食饮料，
靠「复算配比 + 人工命名的 USDA 子集」补齐——这也是为什么库里是 1840 条而不是几万条：
**宁可少而准，也不要多而假**。

数据管线（可复现）：

```powershell
powershell -File tools\fetch-sources.ps1   # 拉取数据源
python tools\build-food-db.py              # 生成 assets/foods_seed.json + 质检报告
python tools\probe-values.py --dishes      # 抽查 42 道菜的推算结果
python tools\check-db-count.py             # 核对设备上的库是否已升级
```

**库会随版本更新到已装用户**：种子文件带内容哈希版本号（`foods_seed.version`），
启动时比版本、按 id upsert，所以升级 App 后新食物会自动补进库里，
**不需要用户清数据重装**。用户记录不受影响（AI 存的食物用 `ai:` 前缀 id，也不会被覆盖）。

## 五、AI 识别：AI 负责「认」，权威库负责「算」

这是本项目的核心设计，也是它区别于「让大模型直接报热量」的地方：

```
照片 / 一句话
   ↓  AI（你配的服务商）        →  只输出：食物名 + 份量克数（+ 可选的每100g值）
   ↓  本地食物库匹配            →  命中就用库里的权威值（成分表 / USDA）
   ↓  没命中 + AI 值通过校验     →  用 AI 值，并**在界面上明确标注「AI 估算」**
   ↓  都没有                    →  保留克数、标「营养待补充」，由你从食物库补
```

AI 给的每 100g 值同样要过本地校验（绝对区间 + Atwater 4/4/9 自洽），
拦住「脂肪 1g 却报 900 千卡」这类幻觉；prompt 里也写明**不确定就填 null，严禁编造**。

### 配置（我的 → AI 设置）

- 内置 7 个服务商预设：腾讯 TokenHub、智谱 GLM、通义千问、硅基流动、Moonshot Kimi、OpenAI、自定义（任何 OpenAI 兼容端点，如 Ollama / one-api）；
- 一个服务商可**分别配「文本模型」与「图片模型」**，两种能力各自绑定用哪家；
- 每个模型都有「测试连接」，可以保存前先验证；Key 只存本机，识别时直连你选的服务商。

实测（2026-10-08，同一句话 / 同一张番茄炒蛋照片）：

| 模型 | 文本 | 视觉 | 识别结果 |
|---|---:|---:|---|
| hy4-preview | 6.3s | — | — |
| deepseek/deepseek-flash | 1.3s | 2.9s | 番茄炒蛋 |
| glm-5.3-flash | 3.0s | 3.5s | 番茄炒蛋 |

默认：文本 `hy4-preview`，图片 `deepseek/deepseek-flash`。

### 兼容处理（都是实测踩出来的）

- 图片一律用 `data:image/jpeg;base64,` 内联，且上传前压到最长边 1024 / 质量 85（原图直传是 6~16MB 的请求体）；
- **参数摘除重试**：部分模型拒绝 `temperature`，4xx 时从自己发出的参数里找出被点名的那项摘掉重发；
- **思考型模型兜底**：`hy4-preview` 这类会先烧推理 token，`max_tokens` 给 4096；若 `content` 为空会退一步去
  `reasoning_content` 里找 JSON；
- 失败提示都带**可执行动作**：401 → 去检查 Key；429 → 稍后再试；超时 → 换更快的模型。

### 降级与出口

- **没配 AI**：回落到离线模拟识别（从本地库随机抽样），结果页顶部**明确写着「这是离线演示识别」**，不糊弄；
- 相机被占用 / 拍照无回调 → 8 秒超时 → 「重试 / 手动录入」；
- Key 无效 / 模型名错 → 直接给「去 AI 设置」入口；
- 相机权限被拒 → 说明页 + 跳系统设置。

### 明确不做语音输入

输入法自带语音转文字，键盘上的麦克风更顺手，App 再塞一个只会多申请录音权限、
多接一个语音模型配置。所以「一句话记一餐」只做**文本解析**：
你用什么方式把字弄进输入框（打字 / 语音 / 剪贴板）都随你，进来之后走的是同一条解析链路。

### 设备实测发现的 6 个问题（已修）

真机跑一遍比读十遍代码有用，下面是模拟器（MuMu，Android 15 / API 35）跑出来的问题：

1. **相机异常会把用户卡死**：模拟器没有摄像头画面时，`ImageCapture.takePicture` 一个回调都不给，
   界面会永远停在「对准食物后按快门」。→ 加了 8 秒拍照超时，超时后主动给出「重试 / 手动录入」。
2. **手动录入会丢记录**：从「相机失败 → 手动录入」进来的路径，加入食物后返回栈里没有结果页，
   于是直接弹回首页，刚选的食物凭空消失。→ 返回栈里没有结果页时自动补一个结果页。
3. **写会话与导航的竞态**：先导航再写会话，ViewModel 随返回栈销毁、`viewModelScope` 被取消，
   协程里的写入被吞掉。→ 改成「写入完成后再导航」。
4. **过期的相机回调会冲掉已经出好的结果**：实测中点了快门（相机不吐帧、回调迟到），
   见没反应就改用相册选图并识别成功，随后那次迟到的 `onError` 回来，
   把结果页覆盖成「拍照失败，重试」——底部还留着 474 千卡的合计，状态自相矛盾。
   → 引入「拍照代次」：每次拍照递增，回调必须带对代次才生效；改用相册/重试都会作废在途回调。
   另外结果页在「已有条目 + 失败提示」并存时，把失败降级成一条内联提示，不再遮挡已有结果。
5. **迁移不幂等会导致 App 永久启动崩溃**：`ALTER TABLE ADD COLUMN` 遇到已存在的列会抛
   `duplicate column name`，一旦发生（迁移执行一半被杀、装过中间版本、恢复过数据库）
   App 每次启动都崩且无法自愈。→ 迁移改成先查 `PRAGMA table_info` 再改。
   顺带用真实升级路径把 v1→v2 的数据保留验证了一遍。
6. **思考型模型的返回被误判为空**：`hy4-preview` 会先烧一大段推理 token，
   给 `max_tokens=2048` 时出现过 `content` 为空、结果全在 `reasoning_content` 里，
   App 直接报「AI 没返回有效内容」。→ `max_tokens` 提到 4096，`content` 为空时回退到
   `reasoning_content` 里找 JSON，并把原始返回打进 debug 日志、失败提示带上具体原因。

## 七、明确不做

登录注册、云同步、社交社区、条码扫描、付费订阅。

**语音输入也不做**：输入法自带语音转文字，键盘上的麦克风更顺手，
App 再做一个只会多要录音权限、多接一个语音模型。用户「说」完落到输入框里，走的还是那条 AI 解析链路。

## 八、已知限制

- **AI 估算的条目不是权威数据**：库里查不到的食物，AI 给的每 100g 值虽然有区间与
  Atwater 双重校验，但仍是模型知识而非成分表读数。界面上会标注「AI 估算（非成分表）」，
  并提供「存进我的食物」把它变成可搜索条目——标签始终保留，不会混进权威数据里。
- **菜肴的配比是家常中位假设，不是实验室实测值**。食材数值来自权威库、算式可复算，
  但一道红烧肉用软五花（349 kcal/100g）是 333，用肋条肉（568）就接近 500 —— 所以结果页必须能改份量。
  当前 42 道菜，要覆盖更多菜，正确做法是继续往 `RECIPES` 里加**有出处、可复算**的配比，
  而不是抄一份菜谱热量表；库里没有的交给 AI 估算 + 标注。
- **覆盖边界**：那份公开的成分表数据只有 1677 条、且全是原料级分类，
  没有小吃/糕点/菜肴/饮料/调味品。所以库里是 1840 条而不是几万条 —— 宁可少而准。
  零食/饮料/西式快餐靠 USDA 人工命名子集补（165 条），中式菜肴靠复算（42 道）。
- 月报表的「较上月」环比暂不展示：需要完整上月同期数据才有意义，宁可不显示也不给错数。
- `FoodRecognitionService` / `RemoteRecognitionService` 这套旧抽象还留在代码里，
  只在「未配置 AI」时作为离线演示使用；接真实识别服务请走 `data/ai/`。
